# v0.4

The 0.4 line modernizes Uvicore's **web stack** (Pydantic v2, the latest FastAPI and Starlette) and sharpens its two most foundational pieces, the **database layer** and the **ORM**, making them more expressive, more portable across database engines, and more robust.

This page tracks every release in the 0.4 line, newest first.

Python 3.12.x, 3.13.x and 3.14.x validated working with Uvicore 0.4.x versions!

---

## 0.4.9

Additive, with one small console-output behavior change (see below).

### Rich-Powered Console Logging

`uvicore.log`'s **console (STDOUT/STDERR) output** is now rendered with
[rich](https://rich.readthedocs.io/) instead of the old `colored`-based
`ColoredFormatter`.  The public `uvicore.log` interface is **unchanged** — every
method (`info`, `notice`, `warning`, `debug`, `error`, `critical`, `exception`,
the `header`/`header2`/`header3`/`header4` and `item`/`item2`/`item3`/`item4`
layout helpers, `line`/`separator`/`blank`/`nl`, `name()`) behaves exactly as
before, it just looks much nicer:

- **`header()` and `header2()`** now render as full-width horizontal **rules**
  with a centered title; **`header3()`/`header4()`** stay as inline styled text.
- **`item()`–`item4()`** render with colored glyphs (`●`, `◆`, `✚`, `▸`) and
  preserve their indentation.
- **`notice()`** gets an `ℹ NOTICE` badge; **`warning()`/`error()`** get `⚠`/`✖`
  prefixes; **`critical()`** gets a `CRITICAL` badge.
- **`separator()`/`line()`** render as clean rules.

**rich is now a base dependency** — it installs with `pip install uvicore`,
**not** gated behind the `web`, `database` or `redis` extras, so console output
is beautiful for every app, including pure-CLI ones.  The old `colored`
dependency, which only the logger used, was **removed** in the same release.

The **file handler is untouched** (still plain
`%(asctime)s ... %(levelname)s ... %(message)s`, so log files stay greppable),
and `dump()`/`dd()` still use `prettyprinter` — rich only powers the console.

**Console behavior change:** `WARNING`, `ERROR` and `CRITICAL` now print to
**STDERR** (previously everything went to STDOUT); `DEBUG`, `INFO` and all the
layout helpers still print to STDOUT.  This is standard practice and lets shells
redirect errors separately, but scripts that captured *only* STDOUT will no
longer see warning/error lines there.  Setting `logger.console.colors = False`
falls back to the previous plain, ASCII, STDOUT-only `StreamHandler` (no rich),
which is handy for dumb terminals or when you want raw output.

## 0.4.8

Purely additive, no breaking changes.  Two web-stack bug fixes surfaced while
rebuilding the framework's `app1` reference web app to exercise the full web
feature set (layouts, composers, partials, macros, named-route `url()`,
`asset()`/`public()`, custom Jinja processors, form POST, guarded routes and a
custom error page).

### Web Error Pages Return the Correct HTTP Status

The default **[web exception handler](../../http/exceptions/handlers.md)** rendered a matching
`errors/<status_code>.j2` (or `errors/catch_all.j2`) template but returned it with the default
`200 OK` instead of the real error status.  A rendered `errors/404.j2` now correctly responds
`404 Not Found`, and the exception's headers are passed through as well.  Only the two
template-rendering branches were affected; the plain-HTML fallback already set the status.

### Redirect-on-Failed-Auth by Route Name

When a web route's guard failed and `unauthenticated_handler.redirect` was configured with a
**route name** (a value containing a `.`, e.g. `wiki.login`), the guard crashed with
`TypeError: argument of type 'URL' is not a container or iterable` — `request.url_for()` returns a
Starlette `URL` object, which the subsequent string operations couldn't handle.  The resolved URL
is now cast to a string, so [redirect-on-failed-authentication](../../http/web/authentication.md#redirect-on-failed-authentication)
by route name works as documented (full-URL redirects were unaffected).

## 0.4.7

Purely additive, no breaking changes.

### View Composers Documented + Dict-Form Registration Fix

**[View composers](../../http/web/view-composers.md)** now have a dedicated documentation page.
A view composer is a class that injects shared context into every view whose name matches a
wildcard (e.g. `wiki/*`), so header/sidebar/footer data can be provided once instead of in every
controller.  The feature already existed but was undocumented.

- **New page** — `http/web/view-composers.md` covers the `@uvicore.composer()` class, its
  `async def compose()` method, registration with `register_http_view_composers()`, wildcard
  matching, the defaults-based context merge (the controller's context always wins), the
  `./uvicore gen composer` generator, and how the design maps to Laravel's view composers.
- **Bug fix** — the **dict form** of `register_http_view_composers({...})` previously called a
  non-existent `self.composers()` helper and raised `AttributeError` during boot.  It now works;
  registering multiple composers at once via a dict is covered by a new test.
- **Scaffold/CLI cleanup** — the `./uvicore gen composer` hint and the composer stub/scaffold
  comments no longer reference the removed pre-0.4 `self.composers()` / `self.views()` helpers;
  they now show the current `register_http_view_composers('<module>', '<views>')` form.

## 0.4.6

Purely additive, no breaking changes.

### Database Engine Disposal at Shutdown (Event-Loop-Closed Fix)

Async database engines are now properly **disposed when the application shuts down**, and
`Db.init()` is now **safe to call more than once**.  Together these fix the noisy
`RuntimeError: Event loop is closed` tracebacks (from `aiomysql`/`asyncpg` connection finalizers)
that could appear when a CLI command exited.

- **New `await uvicore.db.disconnect()`** — disposes one engine (by `connection=` str or
  `metakey=`) or every engine (`all_dbs=True`), closing all pooled driver connections.  Added to
  the `Database` contract.
- **Automatic shutdown disposal** — the database provider's console/http/pytest `Shutdown` event
  handler (previously a no-op stub) now calls `disconnect(all_dbs=True)`, so pooled async
  connections are closed while the event loop is still running instead of being garbage collected
  after it closes.
- **Idempotent `Db.init()`** — a re-init (used by advanced apps to swap a snowflake warehouse at
  runtime) no longer blindly rebuilds every engine, which orphaned the old engines' connection
  pools with no way to ever dispose them.  An engine whose URL is unchanged is **reused**; an
  engine being replaced (URL changed) is **disposed** first; and the metakey's SQLAlchemy
  `MetaData` is **preserved** across re-init so ORM tables already registered on it are not lost.

See [Engine Lifecycle](../../database/db-config.md#engine-lifecycle).  Also backported to 0.3.18
for the 0.3 line.

## 0.4.5

Purely additive, no breaking changes.

### Redis Connection `options`

A Redis connection in `config/package.py` now accepts an optional **`options`** dict whose
key/value pairs are passed straight through as keyword arguments to the underlying
[redis-py](https://redis.readthedocs.io/) async client (`redis.asyncio.from_url()`).  This mirrors
the long-standing `options` dict on a **database** connection (which becomes SQLAlchemy
`connect_args`), giving Redis the same escape hatch for arbitrary client tuning.

```python
    'redis': {
        'default': env('REDIS_DEFAULT', 'wiki'),
        'connections': {
            'wiki': {
                'host': env('REDIS_WIKI_HOST', '127.0.0.1'),
                'port': env.int('REDIS_WIKI_PORT', 6379),
                'database': env.int('REDIS_WIKI_DB', 0),
                'password': env('REDIS_WIKI_PASSWORD', None),
                'options': {
                    'health_check_interval': 30,
                },
            },
        },
    },
```

Any keyword `from_url()` accepts works — `health_check_interval`, `socket_timeout`,
`socket_connect_timeout`, `max_connections`, `decode_responses`, and so on.  Connections that omit
`options` behave exactly as before (the client's own defaults apply).  See the
[Redis](../../deeper/redis.md#configuration) page for details.

## 0.4.3

Hardens the ORM's relation / eager-loading layer and adds **composite (multi-column) joins**
across all three database layers.  Purely additive, no breaking changes.

Tames large OpenAPI schema sets so the Swagger docs stay fast and readable when an app exposes
many models (especially through the [automatic model CRUD API](../../http/api/model-router.md)).
Adds two `config/http.py` `api.openapi` knobs and changes one default.

### Composite (Multi-Column) Relation & Join Keys

Relations and joins can now match on **more than one column**, ANDed together in the order you
declare them.  This is essential for sharded backends such as **Vitess / PlanetScale**, where
every join must include the shard key (e.g. `qgroup_id`, `client_id`) in addition to the natural
key, otherwise the query scatters across all shards and is rejected or times out.

- **ORM relations** — `HasMany`, `HasOne` and `BelongsTo` accept an ordered **list** for
  `foreign_key` and `local_key` (paired positionally):

    ```python
    items: Optional[List[RoItem]] = Field(None,
        relation=HasMany('vfi.core.models.ro_item.RoItem',
            foreign_key=['qgroup_id', 'client_id', 'ro_key'],   # columns on ro_items
            local_key =['qgroup_id', 'client_id', 'key']))      # columns on ros
    ```

    `await Ro.query().include('items').get()` then emits
    `... ON ros.qgroup_id = ro_items.qgroup_id AND ros.client_id = ro_items.client_id AND ros.key = ro_items.ro_key`.
    A single-string key keeps working unchanged (it is simply a one-element composite).  Full
    details in [Composite Relation Keys](../../database/orm-querybuilder.md#composite-multi-column-relation-keys).

- **DB query builder** — `.join()` / `.outer_join()` accept a complete SQLAlchemy expression as
  the `ON` clause (pass an `sa.and_(...)` as the second argument and omit the third).  See the
  new [Joins section](../../database/db-queries.md#joins).

- **SQLAlchemy layer** — documented multi-condition `ON` with `sa.and_()` in
  [SQLAlchemy Joins](../../database/db-sa-queries.md#joins).

### ORM Relation Fixes

- **Non-primary-key `local_key` is now honored.**  Eager-loading a `HasMany` / `HasOne` whose
  `local_key` is a natural key rather than the primary key (e.g. `ros.key` ↔ `ro_items.ro_key`)
  now attaches its children correctly.  Previously the in-memory merge matched children against
  the parent's **primary key**, so any `*Many` keyed on a non-pk column silently came back empty.

- **`*Many` includes combined with `.limit()` / `.offset()` now page correctly.**  `LIMIT` /
  `OFFSET` bound the number of **parent** rows (not the multiplied join rows), and each returned
  parent still gets **all** of its children attached.  Previously
  `.include('items').limit(2)` could collapse to a single parent with no children, because the
  `*Many` join multiplied rows before the limit was applied and the secondary children query
  inherited the same limit.

### Collapsed Input/Output schemas (`separate_schemas`, default `False`)

FastAPI defaults to emitting **two** schemas per model, `Foo-Input` and `Foo-Output`, even when the
two are identical.  With a large model graph this doubles the schema count and roughly doubles the
size of `openapi.json`.

Uvicore now builds the API server with FastAPI `separate_input_output_schemas` pulled from the new
`api.openapi.separate_schemas` config, **defaulting to `False`** so each model is emitted once as
`Foo`:

```python
# acme/wiki/config/http.py
'openapi': {
    'separate_schemas': env.bool('OPENAPI_SEPARATE_SCHEMAS', False),
    ...
},
```

!!! note "Behavior change"
    This changes the default OpenAPI output (model schemas lose the `-Input`/`-Output` suffix and
    are emitted once).  No application code change is required.  If you depend on FastAPI's split
    input/output schemas, set `separate_schemas: True`.

### Hide the Swagger "Schemas" section (`models_expansion`, default `-1`)

A new `api.openapi.docs.models_expansion` maps to Swagger UI's `defaultModelsExpandDepth`.  It
defaults to `-1`, which **hides the standalone Schemas section** at the bottom of the docs, the
single biggest win for UI responsiveness with a large model graph.  Use `0` to show it collapsed,
`1+` to expand.

```python
'docs': {
    'models_expansion': env.int('OPENAPI_MODELS_EXPANSION', -1),  # -1 hides, 0 collapses, 1+ expands
    ...
},
```

This is purely a docs-rendering setting, nothing is removed from `openapi.json`.

### Faster per-operation expand (`model_expansion` + `parameters`)

Hiding the Schemas section fixes the initial load, but expanding a single operation can still lag
the first time while Swagger recursively renders that operation's nested request/response model
tree.  Two more `api.openapi.docs` knobs address it:

- **`model_expansion`** maps to Swagger UI's `defaultModelExpandDepth`.  Set it to `0` to keep each
  operation's model collapsed (instant expand); `1` (Swagger's default) pre-renders one level.
- **`parameters`** is a raw passthrough dict merged into `SwaggerUIBundle({...})`, so any Swagger UI
  setting is configurable without a framework change (e.g. `{'defaultModelRendering': 'model'}` to
  default to the cheaper Schema tab over a computed Example Value).

```python
'docs': {
    'model_expansion': env.int('OPENAPI_MODEL_EXPANSION', 0),
    'parameters': {'defaultModelRendering': 'model'},
    ...
},
```

See [OpenAPI & Swagger Docs](../../http/api/openapi.md#taming-large-schema-sets) for details.



## 0.4.2

Consolidates Uvicore's async HTTP client onto a single library.

!!! danger "Breaking: aiohttp removed"
    The bundled [HTTP Client](../../deeper/http-client.md) switched from **`aiohttp`** to
    **`httpx`**, and `aiohttp` is no longer a dependency.  Code that calls
    `uvicore.ioc.make('aiohttp')` must migrate.  See
    [Upgrade 0.3 to 0.4 → HTTP Client](../upgrade/from-0.3-to-0.4.md#http-client-changed-from-aiohttp-to-httpx).

### HTTP Client: aiohttp → httpx

Uvicore previously bundled **two** async HTTP libraries: `aiohttp` for the runtime client (the
`http_client` IoC service and the Mailgun mail backend) and `httpx` for the in‑process ASGI test
client.  Since `httpx` is already part of the FastAPI/Starlette stack — and is the only one of the
two that can drive an ASGI app in‑process for tests — 0.4.2 drops `aiohttp` and standardizes
everything on `httpx`.

- **Shared client is now `httpx.AsyncClient`.**  Resolve it with `uvicore.ioc.make('http_client')`
  or `uvicore.ioc.make('httpx')` (the old `'aiohttp'` alias is gone).
- **Mailgun mail backend** re‑implemented on httpx (`data=`/`files=` multipart, `(user, pass)`
  basic auth).
- **Requests are awaited directly** — `r = await http.get(url)` — with no `async with`, and the
  response is read synchronously (`r.status_code`, `r.text`, `r.json()`).
- **httpx unpinned** from `0.26.*` to `0.28.*`: the test client now uses the modern
  `AsyncClient(transport=ASGITransport(app=...))` API instead of the removed `app=` shortcut.

The [HTTP Client](../../deeper/http-client.md) guide was rewritten around httpx, with a full
[aiohttp → httpx migration table](../../deeper/http-client.md#migrating-from-aiohttp).

### `environs` upgraded to 15.x — `.env` loading changed

!!! danger "Breaking: how `package/bootstrap.py` loads `.env`"
    `environs` was upgraded to **15.0.1** (the 0.4 line moved it up from 10.x → 14.x → 15.x).  As
    of `environs >= 11`, `Env().read_env()` loads values into **that instance's** private store and
    no longer populates `os.environ`.  An app whose `package/bootstrap.py` reads `.env` into a
    throwaway `Env()` will silently load **nothing** that the config files can see, your
    `env('KEY')` calls fall back to their defaults.  See
    [Upgrade 0.3 to 0.4 → How `.env` Is Loaded Changed](../upgrade/from-0.3-to-0.4.md#how-env-is-loaded-changed-environs-upgrade).

Older `environs` (≤ 9) implemented `read_env()` on top of python-dotenv's `load_dotenv`, which
exported every value into the **global** `os.environ`.  So any `Env()` instance, including the
shared `env` exported from `uvicore.configuration`, saw the values.  Modern `environs` keeps each
instance's values **private to that instance**.

Uvicore's config files (`config/app.py`, `config/package.py`, …) read variables through the
**shared** `env` exported from `uvicore.configuration`:

```python
from uvicore.configuration import env
config = {'name': env('APP_NAME', 'Acme')}
```

So `package/bootstrap.py` must read `.env` into **that same shared instance**, not a fresh
`Env()`:

```python
# Before (broke after the environs upgrade — loads into a discarded instance)
from uvicore.configuration import Env
Env().read_env(base_path + '/.env')

# After (loads into the shared instance the configs actually read)
from uvicore.configuration import env
env.read_env(base_path + '/.env')
```

The bundled app scaffold ([schematic](https://github.com/uvicore/schematic)) and the framework's
own test app were updated, so newly generated apps are already correct.  **Existing** apps must
make this one-line change to their `package/bootstrap.py`.

## 0.4.0

The opening 0.4 release.  The headline change is a **modernized web stack** (Pydantic v1 → v2, FastAPI 0.137, Starlette 1.3), alongside **inline table definitions**, a greatly **expanded query operator set**, cross-database hardening and ORM fixes.

!!! danger "Breaking release"
    The Pydantic v2 upgrade makes 0.4.0 **breaking for application code**, model `update_forward_refs()`, optional-field defaults, `on_event` hooks, custom validators, and serialization method names all change.  Read [Upgrade 0.3 to 0.4](../upgrade/from-0.3-to-0.4.md) before upgrading.

### Modernized Web Stack (Pydantic v2, FastAPI, Starlette)

0.4.0 brings the web stack fully up to date:

- **Pydantic v1 → v2.** The ORM, models, responses and typing layer were ported to Pydantic v2.  FastAPI dropped Pydantic v1 in 0.126, so this had to move together with the framework.
- **FastAPI 0.115 → 0.137** and **Starlette 0.45 → 1.3.**
- **Central model rebuild.** Uvicore now resolves model forward references (relations) for every registered model **centrally at boot**, so you no longer add `update_forward_refs()` / `model_rebuild()` to each model file (keep `from __future__ import annotations` and the bottom-of-file relation imports).
- **Lifespan startup/shutdown.** The HTTP server now uses Starlette's `lifespan` (Starlette 1.0 removed `on_event`); the `uvicore.http.events.server.Startup` / `Shutdown` events fire exactly as before.

This is the source of 0.4.0's breaking changes.  The framework absorbs most of the churn, your `Field()` definitions, relations, tables, query builder and configs are unchanged, but a few app-side updates are required.  See [Upgrade 0.3 to 0.4](../upgrade/from-0.3-to-0.4.md).

### Inline Table Definitions

ORM models can now define their schema **fully inline**, no separate `Table` class required.  Set `__connection__`, `__tablename__` and a raw `__table__` list of SQLAlchemy columns, and Uvicore builds the real `sa.Table` for you, associating it with the connection's metadata and applying any table prefix, exactly like a `Table` class would.

```python
@uvicore.model()
class Post(Model['Post'], metaclass=ModelMetaclass):
    __connection__ = 'wiki'
    __tablename__ = 'posts'
    __table__ = [
        sa.Column('id', sa.Integer, primary_key=True),
        sa.Column('unique_slug', sa.String(length=100), unique=True),
        sa.Column('title', sa.String(length=100)),
    ]
    __table_kwargs__ = {'sqlite_autoincrement': True}   # optional

    id: Optional[int] = Field('id', primary=True, read_only=True)
    slug: str = Field('unique_slug')
    title: str = Field('title')
```

You now have three ways to attach a table to a model, a `Table` class in a separate file, a `Table` class in the same file, or fully inline, and all three produce an identical SQLAlchemy table.  See [DB Tables](../../database/db-tables.md#tables-inline-on-the-model).

### Expanded Query Operators

The `.where()`, `.or_where()`, `.filter()` and `.or_filter()` clauses (in both the [DB Query Builder](../../database/db-queries.md#operators) and the [ORM Query Builder](../../database/orm-querybuilder.md#where)) now support a much larger, case-insensitive, whitespace-tolerant operator set:

- `<>` as an alias for `!=`
- `<=` (previously undocumented/missing)
- `not in` and `not like` as natural-language aliases of `!in` and `!like`
- **`ilike` / `!ilike`** for case-insensitive matching that behaves the same on every database
- `between` / `!between` (value is a `[low, high]` list)
- explicit `is` / `is null` and `is not` / `is not null`

Unknown operators (and unknown columns) now raise a clear, actionable error instead of failing cryptically.

!!! tip
    `like` is case-sensitive on Postgres but case-insensitive on SQLite/MySQL.  Use the new `ilike` operator whenever you want portable, case-insensitive matching.

### Cross-Database Robustness

0.4.0 was validated end to end against real Postgres, MySQL and MariaDB (in addition to SQLite), which surfaced and fixed several portability issues:

- **Postgres just works.** The `postgres` dialect alias is normalized to `postgresql` (SQLAlchemy dropped the old alias), and additional server dialects (`mariadb`, `mssql`, `oracle`, `cockroachdb`) are recognized.
- **Portable auto-increment primary keys.** Inserts no longer send an explicit `NULL` primary key, which SQLite tolerated but Postgres/MySQL rejected.  The database now generates the key on every engine.
- **Type-safe `find()`.** `Model.query().find(id)` coerces the value to the primary key's column type, so a string id (for example from a URL path) no longer errors with `integer = varchar` on Postgres.

### ORM Fixes

- **Multiple `*Many` includes no longer multiply.** Eager-loading several `HasMany` / `BelongsToMany` / `MorphMany` / `MorphToMany` relations in one query previously returned a cartesian product of rows.  Each relation now returns its correct cardinality.
- **`delete()` and `set()` now work for `HasMany`.** Previously these raised for one-to-many relations; they now delete (or replace) the related children like the other relation types.
- **Auto-API create fixed.** The automatic [Model Router](../../http/api/model-router.md) `POST /{model}` endpoint now returns the created record with a real primary key (it previously failed response validation).
