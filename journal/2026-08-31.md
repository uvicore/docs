# 2026-08-31

## Document the PlanetScale/Vitess handshake autocommit change

- **Intent:** PlanetScale changed Vitess to report the correct autocommit value in the initial
  handshake packet, rolling out **2026-09-01**. Vitess previously reported it wrongly, so
  pymysql/aiomysql/asyncmy connections ran autocommit-**ON** despite the driver intending OFF. After
  the change those connections become `autocommit=False`, leaving an implicit transaction open on
  every connection — which Vitess aborts after 20 seconds. Nothing in the docs covered it, and the
  PlanetScale recipe's worked example would have been copy-pasted into a broken connection.
  <https://planetscale.com/docs/vitess/connecting/pymysql-handshake-autocommit>

- **Changed:**
  - `docs/database/recipes/planetscale.md` — added `'autocommit': True` to the worked connection
    example, plus a new **## Autocommit** section: what breaks and why, a table of PlanetScale's
    Option A (`autocommit: True`) vs Option B (`init_command: "set autocommit=0"`) with when to use
    each, and a warning against copying it onto non-PlanetScale connections. Also added a
    long-running-process tip pointing at [Connection Pooling] (new in 0.4.11), since `pre_ping`
    already covers a connection VTGate closed while idle.
  - `docs/database/db-config.md` — new **## PlanetScale** section alongside the existing
    `## Snowflake` one, so the essential two `options` keys (`ssl`, `autocommit`) are discoverable
    from the main config page, linking through to the recipe.

- **The claim the docs deliberately push back on:** it is tempting to assume `autocommit` is True by
  default and that setting it is merely making the implicit explicit. **It is not**, and this was
  measured rather than assumed:
  - `pymysql.Connection` and `aiomysql.Connection` both declare `autocommit=False` as their default.
  - Against a live MySQL with no such kwarg, the session reports `@@session.autocommit = 0`.
  - It only *looks* enabled on PlanetScale today because of the very handshake bug being fixed.
  - Forcing it True is **not cosmetic**: measured against a live MySQL, `INSERT` →
    `connection.rollback()` leaves the row **committed**, versus correctly rolled back at the driver
    default. Both new sections say so explicitly, because "set it everywhere to be safe" is the
    obvious wrong move a reader would otherwise make.

- **Also verified while reviewing the recipe** (no change needed): `'ssl': True` really is valid for
  `aiomysql` — it stores the value as `_ssl_context` and passes it to asyncio's connection open,
  where `True` means the default (certificate-verifying) SSL context. No `ssl.create_default_context()`
  is required, unlike PlanetScale's own generic example.

  sections render (`<h2 id="autocommit">`, `<h2 id="planetscale">`) and the cross-links resolve
  (`../recipes/planetscale/`, `../../db-config/#connection-pooling`).

- **Files:** `docs/database/recipes/planetscale.md`, `docs/database/db-config.md`.
